# VVideo 开发说明：扫描与存储性能

日期：2026-10-09。状态：**施工要求与实现方案；首版已有可执行 Go 代码与行为/规模测试，实际完成范围及限制见 [验证记录](ACCEPTANCE.md)。** 本文是服务端性能实现的规范入口；产品行为、配置和验收目标以 [DESIGN.md](DESIGN.md) 为准。参考项目证据与取舍见 [性能决策](decisions/2026-10-09-scan-storage-performance.md)，分阶段任务及测试契约见 [实施计划](plans/2026-10-09-server-performance.md)。

## 必须遵守的高性能规则

| 规则 | 施工要求 | 验证方式 |
| --- | --- | --- |
| PERF-01 | 先记录目录读取、属性读取、比较、暂存、写入、提交、清理、探测、抽帧耗时；不能只给总秒数 | 分阶段指标；同负载前后比较 |
| PERF-02 | 文件、子目录、数据库结果、待处理任务全部分页或流式读取；内存随批次/工作者/有界栈增长，不随全库条目数增长 | 宽目录、深目录、50 万级索引；队列/堆/FD 峰值 |
| PERF-03 | 不为每文件启动 goroutine，不在每目录再乘一个并发池；统一执行 `scan.parallel` 全局上限 | 可控阻塞的 fake filesystem 检查在途数、取消和收尾 |
| PERF-04 | 一批记录共用事务及预编译语句；正式库单 writer；禁止正常扫描逐文件提交和整库长事务 | 批次数、提交次数、事务持续时间和等待时间 |
| PERF-05 | 文件系统、ffprobe、FFmpeg、网络、等待稳定期均在写事务与共享业务锁外 | 卡住 stat/工具时其他读写请求仍完成 |
| PERF-06 | 无变化复扫不改媒体版本、不重建目录代、不逐条写 last_seen、不重复探测/抽帧 | 精确业务行写入计数、版本和任务唯一键 |
| PERF-07 | 正式库 WAL / FULL、每连接外键、单写/4 只读；仅可丢弃的独立暂存库可降低同步 | 新物理连接设置、断点恢复、完整性/外键检查 |
| PERF-08 | 索引覆盖实际过滤、关联、排序和游标；列表、恢复位置、清理及队列不用深 OFFSET 或重复全表扫描 | 大数据执行计划加深处查询基准 |
| PERF-09 | 新目录结果完成后发布，错误保留旧结果；缺失按两轮健康完整扫描确认，排除不算删除 | 发布故障、离线、根替换、取消、忽略变更测试 |
| PERF-10 | 任务持久化、去重、版本匹配，提交成功才增加计数；不能扫到一个就同步跑工具 | 重启、重复入队、旧任务迟到和失败提交测试 |
| PERF-11 | 原画播放优先，暂停派发新的后台批次；所有缓存、队列和临时文件有上限/回收规则 | 播放竞争测试及长时间资源观测 |
| PERF-12 | 规模测试区分合成 DB、真实文件和真实 NAS；完整索引时间与全部封面就绪时间分别报告 | 记录介质、目录分布、缓存状态、媒体特征和工具版本 |

这些规则约束的是代价与正确性，不是特定函数命名。不能用空实现、跳过媒体、取消耐久性或放宽测试阈值满足性能要求。

## 模块职责与实现顺序

Go 根目录与 [目录规范](../目录规范.md) 一致。以下是将创建的实际职责，不预先生成空包。

| 位置 | 职责 |
| --- | --- |
| `internal/storage/` | SQLite 打开/关闭、连接策略、迁移执行、可观测的写事务入口；不放媒体业务 SQL |
| `internal/scanner/` | 根健康检查、固定目录句柄、分页枚举、属性采集、暂存比较、轮次协调；依赖 library 的索引操作 |
| `internal/library/` | 稳定 ID、内容版本、目录代、可见索引、排序键、分页与锚点；相关 SQL 靠近领域 |
| `internal/jobs/` | 持久延迟队列、幂等认领、版本检查、重试、取消和优先级；确有探测/抽帧共用后创建 |
| `internal/thumbnail/` | 一张百分比封面、FFmpeg 并发、原子完成、容量账目与淘汰 |
| `internal/streaming/` | 原字节 Range、文件版本复核、媒体活动计数；不等待后台扫描 |
| `internal/app/` | 装配 HTTP、扫描器与 worker；不承载大段扫描/SQL 实现 |
| `internal/storage/schema.go`、`tests/` | 内置 schema SQL 与跨包场景；单包测试靠近源码 |

实现顺序是存储及测试接缝 → 流式发现 → 正确发布 → 持久探测队列 → 查询/清理 → 播放竞争压测。不要把 FFmpeg 提前塞入文件遍历热路径。

## 扫描管线

### 资源预算

- 初始内部批次 `B = 128`，仅用于扫描、批量写入及清理；HTTP 仍使用设计中的 100/200 页大小。B 不增加为 YAML 字段。
- 一个遍历协调者、一个正在处理的目录，属性读取共用最多 `P = scan.parallel` 个 worker；首版每页采集完再提交，不预读无界页面。P 不乘目录数，也不控制 ffprobe/FFmpeg。
- 每页只保留名称、类型、文件身份、大小、mtime 等轻量结构，不读完整视频、图片或内容哈希。扩展名过滤先于昂贵探测；安全识别目录所需的属性读取仍可能发生。
- 子目录以已发布索引提供稳定 ID，仅把本轮成功观测到且未排除的目录加入可分页的遍历候选；深度优先遍历，栈帧保存目录 ID 与游标，不附带全部后代路径。候选可留在暂存表，不能用全量切片代替；暂存复用时不得清掉祖先尚未遍历的子目录游标数据。内置深度上限初始 1,024，超限标记该分支失败、保留旧索引。若栈帧缓存一页，也必须将 `B × 深度` 成本计入预算。
- 前后两遍观测的数据放独立的**本机磁盘**暂存库，一轮复用；建议固定在 `storage` 所在目录的受管 `.scan-tmp/` 子目录。与缩略图 LRU 分开，权限限制到服务用户，不能落入源媒体。维护空间账目，空间不足停止本轮并保留旧索引。
- 暂存不存媒体字节，可随失败或重启删除；正式库中已提交但未发布的候选则按状态回收，不能仅删暂存文件就假定恢复完成。检查临时空间、正式库、WAL 和新旧目录代的叠加成本。

### 单轮流程

```text
取得唯一轮次资格，冻结本轮 media / ignore，记录根身份和配置修订
对每个健康根：
  用分页游标遍历目录；每目录持有可取消的扫描资格
  读取当前已发布基线到暂存，结束正式库读事务
  逐层打开并核对目录身份；第一遍 ReadDir(B) + 有界属性读取
  重新从头枚举同一目录身份；第二遍观测与第一遍逐项比较
  复核路径链与根健康；比较基线，得到新增、变更、缺失候选
  若无变化：仅更新目录/轮次状态，不碰每个媒体行
  若有变化：分页持久构建候选，完成后校验基线并发布目录代
  向持久队列记录新增/变更版本的后续工作；清理旧代也分批让步
根的全部应扫描范围成功且前后健康：标记该根本轮成功
只有已确认成功的根轮次可以推进缺失确认；失败/离线轮次打断连续性
记录统计，关闭句柄和暂存；释放轮次资格
```

关键约束：

1. 使用正数批量读取 API，不把 `os.ReadDir(path)`、`ReadDir(-1)` 或默认全量排序的遍历入口当流式读取。正确处理“返回一批数据同时返回 EOF”；普通读取错误意味着本目录观测失败。
2. 元数据可能需要 NAS 往返，也可能已在目录读取阶段发生。每一遍只采集一次所需属性并复用；不要为日志、路径显示或数据库准备再次 stat 同一项。
3. worker 的结果按输入下标归位；出现错误停止继续派发，回收已派发工作后返回稳定的错误结果。不能提前关闭仍被 worker 使用的目录描述符，也不能以丢弃 goroutine 的方式假装取消完成。
4. 不在共享锁内等待目录资格、NAS 或数据库连接。每目录资格阻止重复扫描；全局锁只保护短小状态，慢目录不阻塞已有索引读取。
5. 文件身份使用根身份、相对路径、设备/inode、大小、mtime 与 ctime（秒/纳秒），网络文件系统上的稳定性须实测。ctime 只守卫版本，不作拍摄时间。不能单凭 inode 猜测跨路径改名；同时保留全部观测元数据的内容替换仍可能漏检，保留明确的强制刷新机制。属性来自已有 stat，算法仍 O(1)，不新增逐文件内容读取。
6. 双遍不一致时最多完整重试一次；权限错误、空间不足或取消直接结束本目录。独立目录可继续，根身份变化停止该根。根部分失败允许成功目录发布新增/变更，但本根本轮不推进任何缺失确认。
7. 文件 60 秒稳定性检查放持久延迟任务，采用两次属性观测；不在目录扫描中 sleep 60 秒，不为每文件保留等待协程，也不把连续两遍扫描当已满足稳定时间。

### 目录发布与缺失

至少区分三种版本：**稳定媒体 ID** 供浏览历史定位；**媒体内容版本** 供任务、Range 和缓存隔离；**目录列表修订** 供分页及排序一致性。扫描成功次数不能代替这些版本。

- 按目录暂存差异和构建下一代，使用事务切换可见状态。多个已提交构建批次在发布前不可被普通列表、计数或任务消费者当作有效媒体。
- 发布时复核目录基线及有关祖先证据；只有其他无关目录变化，不应导致本目录无条件重扫。版本冲突要重新读取基线，不能覆盖并发有效结果。
- 无变化复扫不生成新目录代，不更新全部 `last_seen` 或媒体版本。可以更新每目录的扫描时间、根轮次摘要和少量状态。
- 缺失先写候选。按每个根的**连续完整健康轮次**确认，排除分支不算缺失；恢复出现清零，失败/离线轮次打断。轮次成功标记先持久化，缺失候选再按目录/批次处理，重启可幂等继续；禁止扫描到一半就应用删除。
- 两轮确认后只隐藏/标记不可用并保留索引；配置移除、ignore 新增和真实缺失使用不同原因。ignore 改动不应通过“本轮未见到”累加缺失。具体可见行为沿用设计。
- 健康父目录完整观测确认某子目录缺失时，只建立该子树的缺失候选，不再遍历旧索引中的该子目录；否则会因持续 ENOENT 把每轮都判为失败，永远无法确认缺失。权限不足、父目录观测不完整及挂载健康不明不属于这种情况。确认后子树可见性和任务认领须同时遵守祖先状态，避免递归逐行提交或漏出孤立媒体。
- 列表内使用一致的已发布版本，不能把新文件大小与旧内容版本混在一起。播放仍重新核对实际文件；数据库快照不能保证源文件之后未被外部改写。
- **发布成本必须单独测量。** 初版可按参考的目录代方式实现，但最终事务只处理索引定位出的差异，不再执行整库比较。大量差异仍可能产生长事务；若影响播放门槛，须把更多数据预写成带版本记录、缩小最终可见性切换，再通过故障与旧版本测试。不能只把一个长事务拆成用户可见的半目录。
- 一个超大目录中仅一项变化，也要测构建及回收代的放大成本；“只重建变化目录”不等于“只写变化行”。探测结果补齐时只批量更新受影响媒体及排序修订，禁止每返回一个 ffprobe 结果就复制完整目录代。

## SQLite 与任务写入

### 连接、事务和持久性

初始化SQL的单一来源是`internal/storage/schema.go`中的常量，随Go服务编译。仅对`PRAGMA user_version=0`的库在单个事务执行；成功仍为版本1，已有版本1不重复建表，较新版本拒绝打开。源码归属调整不改变表、索引、事务边界或运行配置。

- 正式库在本机文件系统，单服务实例拥有写权限；初始化后验证实际 WAL 设置。单写连接加 4 个只读连接，连接级配置必须覆盖新开的物理连接，不能只对第一个连接执行 PRAGMA。
- 正式库使用 `synchronous=FULL`、外键检查与内置 5 秒 busy timeout。读池使用只读模式及 `query_only`；数据是否只读不能仅靠调用方约定。不要静默退回非 WAL 模式。
- 写批次完成内存数据准备后才申请 writer：开始事务 → 复用语句逐条绑定 → 写同批状态/计数 → 提交 → 发布成功指标。失败回滚整个批次，调用方收到错误。扫描普通构建/清理批次最多 B 行；目录最终发布事务须独立统计，不谎报也受 B 行限制。
- 一个批次反复执行准备好的 SQL 已经能减少提交与解析成本；无需先引入巨型多值 INSERT。若使用多值绑定，要按所选驱动实际变量限制分批。幂等冲突须指定真正的唯一键，不以宽泛 `IGNORE` 吞掉必填字段或外键错误。
- 文件和工具 I/O 不进入事务。读改写操作在同一个正式库事务完成，不能先读缓存然后盲写。禁止持有 writer 时调用一个还要等待同一 writer 的辅助函数。
- 统计仅计算已提交行；重试不得重复增加计数。全量未变媒体不写观察时间；扫描摘要按目录或节流更新，日志不逐文件输出成功记录。
- 单个 API 最多物化一页结果，关闭 rows/事务后再向网络发送；避免慢客户端长期占用读事务。复制扫描基线的读事务仅做本机数据读取，结束后才访问 NAS，并记录其最长持续时间。
- 初期保留 SQLite 默认自动 checkpoint 并测量。记录 WAL 大小、checkpoint 进度、busy 及长读事务；不在每个批次后强制 TRUNCATE/VACUUM。若调整策略，必须防止旧读快照导致 WAL 无限制增长，先解决长读事务和写入节流。

### 队列与媒体探测

建议持久任务至少有 `media_id`、`content_version`、`kind`、`parameters_hash`、`state`、`next_attempt_at`、`attempts` 和认领信息。唯一键由媒体 ID、版本、任务类型和参数组成；缩略图参数包含百分比、尺寸、质量。

1. 扫描只产生新增/变更的工作意图。工作意图与对应索引状态可靠关联；推荐随构建批次写入待发布任务，消费者只认领已发布版本。不能索引提交后只发内存 channel，造成重启永久漏任务。
2. 内存队列只保留有限认领窗口；更大积压留数据库。按状态/到期时间/ID 索引认领，不把所有 queued 行加载到内存。租约/认领及计数在同一短事务提交，取消和重启可重试。
3. 等稳定 → 探测 → 保存元数据 → 封面排队分阶段；首轮可以先显示路径、mtime 与占位状态，不能为等全部封面阻塞建库或 API。
4. 工具执行前后检查版本；旧版本迟到结果丢弃，不能覆盖新媒体的时间、封面或时长。输出先写受管临时文件，校验并原子完成后才标记 ready；数据库提交失败的孤儿输出可识别回收。
5. 完全未变且已完成的媒体不重新执行工具。失败重试受设计中的上限限制；缓存淘汰不会清掉“这个版本曾成功处理”的状态，也不会在下轮扫描触发整库补图。
6. 每视频只生成一张封面。媒体路径及流复制不参与数据库事务；图片的拍摄时间/尺寸提取也受工具/工作池预算限制，不能因其不是视频就无界并发。
7. 拍摄时间补齐会改变默认排序；同批变更合并修订通知，客户端按媒体锚点保位。当前实现：探测只写版本元数据，排序键改变的任务停在 `probed` 状态，由 `Index.PublishProbedTimes` 每 20 秒批量写入排序键，每批每目录递增一次 revision。更新排序键与列表修订原子一致，并测试它与扫描发布交错的结果，防止发布旧排序键覆盖新探测结果。

## 索引、分页与清理

以真实查询推导迁移里的索引，避免一次加齐所有可能的列组合。至少为下列路径检查执行计划并进行规模测试：

| 路径 | 候选索引形状 / 要求 |
| --- | --- |
| 默认拍摄时间倒序 | 目录、可见代或状态、物化有效时间、稳定 ID；有效时间包含 mtime 回退，ID 解决相同时间并列 |
| 名称/mtime 排序 | 同一目录范围内相应排序键与 ID；明确大小写、自然排序与反向语义，表达式/排序规则要与索引一致 |
| 恢复浏览锚点 | 先按媒体 ID 取排序键，再取前后有限页；不能 `COUNT(prefix)` 后使用 OFFSET 走到中间 |
| 扫描子目录 | 父目录、目录类型/可见条件、ID 游标 |
| 任务认领 | 待处理状态、到期时间、ID；版本/任务参数唯一键 |
| 旧代/候选回收 | 目录、代、ID 或专用候选索引；外键被引用列具备反查索引 |
| 缩略图 LRU | 状态、最后访问时间、ID；容量账目增量更新，访问时间合并写入 |

游标携带目录、排序、方向、目录修订和最后排序键/ID，服务端校验其匹配。修订改变时明确要求按锚点重定位，不能无声混页。正反序、重复时间、十项分组边界均需验证。恢复深处位置时不得为计算全局组号扫描全部前缀；通过预计算分组锚点或有界邻近重组解决，并测试连续翻页无重无漏。

整库扫描与统计允许有一次线性工作，禁止每目录/每页重复全库线性查询。`EXPLAIN QUERY PLAN` 中一次扫描小暂存表或目标范围并非一定有错；重点禁止反复扫描无关大表与全目录临时排序。测试断言相关索引/范围性质，不绑定整段随 SQLite 版本变化的输出。

清理采用候选 ID 游标与小事务，每批重新验证仍未发布/无人使用；故障不删除当前代或有效任务。不每扫描一个小目录就搜索整库孤儿。启动时回收中断构建，后台清理可暂停；若积压达到空间保护线，停止新构建并报告原因，不能任其永久增长。

精确整库数量和树状统计不放在每次列表请求中。需要时异步/按需汇总并有界缓存，按已提交修订失效。缓存账目通过增删更新，定期低优先级核对；禁止每次读取“缓存占用”就遍历缓存目录。

## 播放优先与观测

调度语义沿用设计：媒体原字节请求（含预取）活跃期间，暂停新的后台扫描页、探测和抽帧任务；最后请求结束后冷却 10 秒再继续。不强杀在途任务，已开始的有限批次允许收尾。前台封面与后台抽帧共享 `cache.parallel` 总上限。

暂停发生在拿新工作前，不持锁/事务等待恢复。持续播放导致扫描长时间暂停时，恢复前重新核对根身份和当前目录观测，必要时废弃本目录暂存重扫，不能拿过时快照直接发布。cron 仍不叠加新轮次。

每轮至少记录：文件/目录数、忽略数、失败范围、新增/变更/缺失候选/确认数、无变化目录数、实际探测/抽帧次数，以及下列指标：

- `readdir`、属性采集、复核、暂存、差异查询、目录构建、正式库排队/执行/commit、最终发布、清理各阶段墙钟耗时。
- 当前/峰值 worker、队列深度、事务行数、累计提交数、失败/取消/版本冲突次数。
- 进程 RSS、Go live heap/累计分配、goroutine、FD、DB/WAL/暂存/缓存字节与 checkpoint 状态。
- 同期目录页/锚点查询的 p50/p95/p99、媒体首字节、拖动恢复、实际播放缓冲中断。

并发任务耗时之和不等于墙钟总时长；各阶段可能重叠，不强行凑成 100%。业务日志按轮次/目录摘要节流，敏感完整路径和文件名不进入默认性能报告。

没有目标 NAS、有效媒体和真机数据时，只能证明算法约束、故障行为与本机基准。完整索引扫描、全部元数据可用、全部可生成封面完成是三个独立里程碑，不用最短的那个代表整个建库耗时。
